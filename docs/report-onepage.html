Chat filter: accuracy defect

Ragnarok: Rebirth Global  ·  reported by a player 2026-09-10
The filter matches raw substrings, so ordinary words containing a blocked fragment are censored — cucumber is blocked because of three letters inside it — while the same design lets deliberate evasion straight through. It is simultaneously too aggressive and too weak, and both symptoms have one cause.

Root cause

The list is 95,660 entries, 93.4% Chinese — market-compliance material (political terms, regional gambling domains, precursor chemicals), appropriate for the market it was written for. Rebirth launched in China in Dec 2025 and globally in Jul 2026; the list travelled with the build.

11,872 entries are two characters long; 497 are a single character. As substrings they sit inside thousands of ordinary words: te in ignite, ll in skills, ur in curse, 日 in 日光. Chinese suffers the identical defect — 日 fires 438 times inside the game's own Chinese names — so a fix helps that build too.

Not a request to filter less

Against ten common obfuscation strategies the list catches 22.9%. Spaced-out text, full-width characters and homoglyphs pass untouched. Of 25 common English profanity terms tested, 6 are present at all.

So it blocks cucumber and passes f u c k. Fixing this makes the filter more accurate in both directions, not more permissive.

What would fix it

  1. Run the self-test. ~40 lines, no dependencies, nothing to adopt. Enforces one invariant: no string we authored may be flagged by our own filter. Has a ratchet, so it goes into CI today.
  2. Rank your own entries by damage. False positives are extremely concentrated — on the copy measured, 20 entries caused 89% of them, and only 191 of 5,695 needed any change. Emits a CSV with per-entry blast radius and a recommended action: scope to locale (deletes nothing), whole-word only, or delete.
  3. Fix the matching. Word boundaries plus a rescue allowlist. Same vocabulary, no new words: dictionary false positives 37.1% → 0.0%; with a lexicon generated from your own localization, own-content false positives 46.1% → 0.0% while obfuscation recall rises 22.9% → 84.3%.

Two things worth knowing

Nothing here needs a client update. The filter check is already a server round trip — the client sends candidate text and receives a masked string back. All of the above changes only the server side of that call. No client build, no store review.

59.6% of the list cannot affect any outcome, because a shorter entry already matches inside each of those 57,051 entries. Substring matching has collapsed a 95,660-entry list into the behaviour of its shortest ~38,000. Word-boundary matching does not weaken the list — it restores the other 57,051 to usefulness.

One caveat, stated plainly. The list analysed is the copy shipped in the client, and it does not fully match what the server enforces: cucumber is blocked live, yet the responsible fragment is absent from the client copy. So please don't action any specific row we name — run the tools against your own list. The class of defect is proven by the live observations above and holds regardless; only the exact rows are yours to generate.
